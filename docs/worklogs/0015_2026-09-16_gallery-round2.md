## Un-star (reversible stars)

- **API:** `DELETE /api/tracks/:id/star` takes a star back — floored at
  0 (a fresh track can't go negative), `{id, stars}` like the POST.
  `unstar()` in all three drivers (sqlite `MAX(0, stars-1)`, pg
  `GREATEST(0, stars-1)`, memory `Math.max`), pinned in the shared
  store-conformance suite and the HTTP contract test.
- **Client:** the ☆/★ button toggles — POST to star, DELETE to unstar;
  `m4wd.starred` gains `removeStarred` (same never-throws contract).
  Re-starring works; the state survives reopen.

## Card previews (thumbnails)

- Each gallery card renders the actual track in an 80×60 canvas — same
  sprite pipeline as the palette chips (`imageFor` + `drawPieceArt`
  fallback), pieces drawn at their real positions/rotations.
- List rows carry no track body (metadata-only by design, pinned), so
  each card lazy-fetches `GET /api/tracks/:id`, parses via
  `spritesFromRow`, and draws; results are cached per session and at
  most 4 row fetches run at once. Rows that left the DOM (sort switch)
  are skipped at draw time.
- The fit math is pure: `thumbFit(sprites, w, h)` in gallery.js —
  bbox over every piece's rotated footprint, uniform scale into a
  padded box, centering offsets. Unit-pinned (rotation swaps w/h,
  multi-piece spans, empty → null).
- **Bug found while wiring (two rounds):** the thumb scheduler first
  checked `isConnected` on a *function* (always false → nothing ever
  fetched), then checked the canvas at *queue* time — but rows are
  queued inside `galRowEl` before the list appends them, so every entry
  was dropped. Fixed by pumping on a `queueMicrotask`, after the render
  loop connects the canvases. The e2e pixel probe (non-transparent
  pixels on the thumb canvas) fails on both broken variants.
