## The vert inconsistency (found before generating)

INVARIANTS demands seam alignment, but the catalog carried two vert
conventions in the rudoc drawer:

- corners (R1C45I150, R1C90I150, R2C45I150, R3C45I115) and the R2/R3 axis
  entries put verts **on the road centerline** (corner verts ride the R
  circle by construction — same as the Cor family);
- the #8 measured entries (R1S250, R1REntry, R2Ramp5..45) put verts ~0.6
  above the footprint bottom edge (y = -6 / -11.9).

Art cannot bridge that: rect_family centers the road in the footprint, so
R1S250's road cannot pass through its own vert (11.5-wide road at y=-6
overflows the 13.3-tall footprint by 5+). Welded straight↔corner joints
misaligned roads by ~6 units.

**Fix:** verts of R1S250 / R1REntry / R2Ramp5..45 moved to y=0 (the only
value consistent with footprint, corners, R2/R3 entries, and the main
families). `tests/unit/pieces.test.js` now asserts the y-midpoint invariant
so the convention is self-enforcing.

## Verification

- regen byte-identity: the pre-existing 67 SVGs unchanged (cmp loop clean);
  only 8 files added.
- **Seam probe** (new technique, built for this change): composes welded
  pairs exactly as the app places them — placements computed by the app's
  own `geometry.js` (orientAngle/vertexOf) — rasters the composition, and
  samples along the seam normal: road top/bottom edges and lane-divider
  positions must match left vs right. Results:
  - R1S250→R1C45I150, R1C45I150→R1S250 (45° joint), R1S250→R1C90I150,
    R2S250→R2R250, R3S250→R3C45I115, Str1→Str1 (control): all align ≤0.2px.
  - R1REntry→R2S250 (1L→2L mixed width) fails by design: 1L road centers on
    the 2L centerline — the lane-bundle question deferred to the owner.
- `inspect.py`: 75 checked, 0 failures (goldens frozen for the 8 new).
- npm test 111/0; e2e 37/37 (weld test updated to the new verts).
- Cache busters: sprites ?v=27, main.js ?v=42.
