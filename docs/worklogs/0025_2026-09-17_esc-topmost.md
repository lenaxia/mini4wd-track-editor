# 0025 — Esc peels one dialog at a time

**Date:** 2026-09-17
**Triggered by:** Owner ruling — "Esc should only clear top most
dialog" (flagged as a deliberate-decision item by the #51 review).

## Why stacked dialogs died in pairs

Two closers ran per press: the app's document keydown handler closed
the first `dialog[open]` in DOM order, and the browser's native
Esc-cancel — the keydown's DEFAULT action — then cancelled whatever
modal was topmost AFTER the handler ran. Probe evidence: stack
[publishDialog, libraryDialog], one Esc → two close events, both
dialogs gone.

## Fix

- openDialog/closeDialog maintain an open-order stack;
  topOpenDialog() prunes entries closed out from under us (the native
  path doesn't pass through our helpers).
- The Esc handler closes ONLY the stack top, and `preventDefault()` is
  the load-bearing half — it suppresses the native cancel that would
  otherwise peel the newly-exposed modal next (the kebab-menu handler
  already relied on exactly this mechanism).
- One press, one dialog: probe shows Esc → [libraryDialog], Esc → []
  ; pinned in the library spec (rename-cancel keeps the library, a
  second Esc closes it).
