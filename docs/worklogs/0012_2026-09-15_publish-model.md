# 0012 — Publish model: server storage becomes explicit

**Date:** 2026-09-15
**Triggered by:** Owner ruling — "I don't think saving every single track
someone makes is a good idea. We should have a publish feature which
actually persists a track and then they can edit from there."

---

## Model

- **Unpublished = local only.** Autosave stays in localStorage; the server
  mirror is gone. Zero `/api/tracks` traffic from an unpublished browser
  (pinned by a page-hermetic e2e that watches the page's requests).
- **Publish = explicit.** Track menu → "Publish to server" → name dialog →
  POST `/api/tracks` → the row persists; the binding `{id, name}` lives in
  localStorage (`m4wd.published`). Publishing again renames (PUT).
- **Published tracks live-edit.** Once bound, every autosave mirrors to the
  row under its name — same generation-guarded retry machinery from 0010,
  now carrying the chosen name.
- **My published tracks**: menu library lists server rows
  (name · pieces · length · updated); tapping loads it onto the canvas and
  ADOPTS the binding, so a published track follows the user across
  browsers. **New track** drops the binding and clears the canvas.

## Notes

- The old `m4wd.trackId` auto-mirror is removed; its e2e became the
  publish/live-sync pair. Storage unit tests now pin the gating: no
  binding → zero fetches; publish POST→PUT; bound mirror carries the name;
  retry/give-up; unpublish stops the mirror.
- The server API is unchanged (POST/PUT/GET already fit); the model moved
  entirely into the client.
- Known follow-ups: rename could also live inline in the library; delete
  from the library; author field when identity ever matters.
