# 0023 — One-request sprite boot (preview rate-limit resilience)

**Date:** 2026-09-16
**Triggered by:** Owner report — placeholder art in the dev preview,
suspected 429s, nothing in console or server logs.

## Diagnosis (evidence)

The preview proxy rate-limits request bursts before they reach the
app: the owner's 22:14 visits logged `GET / ok` three times while
**zero** of the ~75 boot-time `/api/sprites/*` requests arrived. The
app swallows those failures and falls back to the procedural art —
hence placeholders with clean console and server logs (the log only
prints what reaches us).

## Fix

- `GET /api/sprites` returns the WHOLE set (`{files: {name: svg}}`) in
  one json request (~412 KB uncompressed, 75 files). `?h=<digest>` →
  immutable, else no-cache — same hash-addressing convention as the
  per-file route, which stays (static-only servers, self-healing).
- `spriteBundle()` in cache.js: digest = sha of the canonical
  manifest; every file's bytes are sha-verified against the manifest
  before use and banked into CacheStorage under the per-file URL — a
  bad bundle drops to the per-file path, never trusted. `preloadImages`
  consumes the bundle when manifest mode is on; per-file remains the
  fallback.
- Boot sprite traffic: 75 requests → 1 (2 with the manifest fetch);
  later boots serve from CacheStorage with zero sprite requests.

## Follow-ups

- The preview now also regenerates `assets/manifest.json` (gen-manifest
  runs at deploy in CI; the ad-hoc preview dir had none, forcing the
  per-file path).
- gzip/brotli on the server would shrink the bundle further (the
  static server has none today).
